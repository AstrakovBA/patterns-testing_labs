# Паттерны проектирования

В игре применены одиннадцать паттернов: Одиночка, Строитель, Фабричный метод, Прототип, Адаптер, Мост, Компоновщик, Декоратор, Фасад, Приспособленец и Заместитель. Они распределены по задачам хранения настроек, сборки уровня, создания объектов, обработки ввода, отрисовки и игрового процесса.

Примеры кода показывают действующие классы проекта. Их можно запускать из каталога `coin_collector_app`, предварительно установив зависимости из `requirements.txt`.

## Одиночка (Singleton)

**Где находится:** `coin_collector/settings.py`, классы `SettingsManager` и `GameSettings`.

**Задача:** настройки звуковых эффектов и сложности должны быть общими для меню и игрового процесса. Если бы каждая часть приложения создавала собственный менеджер, значения могли бы разойтись: меню изменило бы одну копию, а игра продолжила бы использовать другую.

**Как работает:** метод `__new__` сохраняет созданный экземпляр в атрибуте класса и при последующих вызовах возвращает тот же объект. Флаг `_initialized` также не позволяет повторно загружать настройки при получении этого объекта.

```python
manager_from_menu = SettingsManager()
manager_from_game = SettingsManager()

assert manager_from_menu is manager_from_game

manager_from_menu.toggle_difficulty()
print(manager_from_game.settings.difficulty)  # то же общее значение
```

Существенная часть реализации:

```python
class SettingsManager:
    _instance: SettingsManager | None = None

    def __new__(cls) -> SettingsManager:
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self) -> None:
        if getattr(self, "_initialized", False):
            return
        self.settings = self._load()
        self._initialized = True
```

При первом создании менеджер загружает JSON-файл, а методы `toggle_sound()` и `toggle_difficulty()` сохраняют изменения. Поэтому значения доступны и в меню, и в текущей партии, и после перезапуска приложения.

**Почему здесь уместно:** настройки представляют общее состояние одного приложения, и отдельное хранилище для каждого экрана не нужно.

**Ограничение:** Одиночка вводит глобальную точку доступа и общее изменяемое состояние. Для приложения с несколькими профилями или несколькими одновременно открытыми игровыми окнами менеджер следовало бы создавать и передавать явно, а не ограничивать одним экземпляром.

## Строитель (Builder)

**Где находится:** `coin_collector/level.py`, класс `GameLevelBuilder`.

**Задача:** собрать арену из начальной позиции игрока, монет и опасностей, не перегружая конструктор уровня длинным списком позиционных аргументов.

**Как работает:** строитель хранит промежуточное описание уровня. Вызовы `set_player_start()`, `add_coin()` и `add_hazard()` добавляют в описание отдельные части. `build()` проверяет координаты и создаёт готовый объект `GameLevel`.

```python
factory = ArcadeObjectFactory()
size = (960, 640)

level = (
    GameLevelBuilder(factory, size)
    .set_player_start((480, 360))
    .add_coin((120, 150))
    .add_coin((840, 150))
    .add_hazard((480, 220))
    .build()
)

print(len(level.coins))    # 2
print(len(level.hazards))  # 1
```

Строитель отклоняет некорректные координаты до создания объектов:

```python
builder = GameLevelBuilder(factory, size)
builder.add_coin((0, 0))  # за границами игровой арены
builder.build()           # ValueError: координаты объектов должны быть внутри
```

Функция `build_default_level()` использует тот же строитель для стандартного расположения предметов. Чтобы изменить расстановку, достаточно изменить описание уровня, не переписывая цикл игры и правила движения.

**Почему здесь уместно:** состав и размещение объектов уровня можно задавать по шагам, а результат сборки проверять до начала игры.

**Ограничение:** для очень простого уровня из единственного фиксированного объекта строитель был бы лишним. В этой игре он полезен, потому что уровень содержит несколько типов объектов и проходит проверку границ.

## Фабричный метод (Factory Method)

**Где находится:** `coin_collector/factory.py`, классы `GameObjectFactory` и `ArcadeObjectFactory`.

**Задача:** отделить код сборки уровня от выбора конкретных классов игровых объектов. Строителю достаточно запросить «создать монету» или «создать опасность»; ему не нужно вручную вызывать конструкторы каждой сущности.

**Как работает:** абстрактная фабрика объявляет метод `create()`, а конкретная фабрика решает, какой экземпляр вернуть для каждого значения `ObjectKind`.

```python
factory = ArcadeObjectFactory()

player = factory.create(ObjectKind.PLAYER, (480, 360))
coin = factory.create(ObjectKind.COIN, (120, 150))
hazard = factory.create(ObjectKind.HAZARD, (480, 220))
```

Упрощённое представление фабричного метода:

```python
class GameObjectFactory(ABC):
    @abstractmethod
    def create(self, kind: ObjectKind, position: tuple[int, int]) -> GameObject:
        raise NotImplementedError


class ArcadeObjectFactory(GameObjectFactory):
    def create(self, kind: ObjectKind, position: tuple[int, int]) -> GameObject:
        if kind is ObjectKind.PLAYER:
            return Player(position)
        if kind is ObjectKind.COIN:
            return self._coin_prototype.clone_at(position)
        if kind is ObjectKind.HAZARD:
            return self._hazard_prototype.clone_at(position)
        raise ValueError(f"Unsupported game object kind: {kind!r}")
```

`GameLevelBuilder` принимает `GameObjectFactory`, то есть зависит от интерфейса создания, а не от конкретной фабрики. Это позволяет добавить фабрику другого режима или набора объектов без изменения последовательности шагов построения уровня.

**Почему здесь уместно:** создание игрока, монет и препятствий сосредоточено в одном месте, а строитель уровня остаётся универсальным.

**Отличие от Прототипа в проекте:** Фабричный метод выбирает операцию создания по типу объекта; для части типов выбранная фабрикой операция, в свою очередь, клонирует заранее подготовленный прототип.

## Прототип (Prototype)

**Где находится:** методы `clone_at()` классов `Coin` и `Hazard` в `coin_collector/entities.py`; прототипы хранятся в `ArcadeObjectFactory`.

**Задача:** быстро создавать однотипные монеты и опасности с теми же начальными параметрами, но с независимыми координатами и состоянием анимации.

**Как работает:** `clone_at()` копирует объект, создаёт для копии отдельный `pygame.Rect`, задаёт новую позицию и сбрасывает время анимации.

```python
first = factory.create(ObjectKind.COIN, (120, 150))
second = factory.create(ObjectKind.COIN, (840, 150))

assert first is not second
assert first.rect is not second.rect
assert first.rect.center == (120, 150)
assert second.rect.center == (840, 150)
```

Реализация клонирования монеты:

```python
def clone_at(self, position: tuple[int, int]) -> Coin:
    clone = copy.copy(self)
    clone.rect = self.rect.copy()
    clone.rect.center = position
    clone.animation_time = 0.0
    return clone
```

`ArcadeObjectFactory` создаёт по одному исходному экземпляру монеты и опасности, после чего выдаёт независимые копии. Это особенно важно для `rect`: если разделить прямоугольник между монетами, изменение позиции одной монеты затронет другую.

**Почему здесь уместно:** на уровне несколько предметов с общими базовыми параметрами, но собственными позициями и анимацией.

**Ограничение:** неглубокое копирование подходит, пока изменяемое состояние сущности состоит из полей, которые явно копируются в `clone_at()`. Если в сущность добавить изменяемый список или вложенный объект, который должен принадлежать только копии, его тоже нужно будет копировать.

## Адаптер (Adapter)

**Где находится:** `coin_collector/input_adapter.py`, классы `PygameInputAdapter` и `InputFrame`.

**Задача:** преобразовать специфические события Pygame в небольшую, удобную для игровой логики структуру ввода.

**Как работает:** адаптер принимает очередь событий и состояние клавиш, распознаёт WASD и стрелки, а затем возвращает направления движения, именованные действия и признак запроса на выход.

```python
adapter = PygameInputAdapter()
frame = adapter.read(pygame.event.get(), pygame.key.get_pressed())

if frame.movement == (1, 0):
    print("игрок движется вправо")
if "confirm" in frame.pressed:
    print("нажата клавиша выбора")
if frame.quit_requested:
    print("запрошено закрытие игры")
```

Игровая логика получает объект с понятными действиями, а не должна самостоятельно сопоставлять клавиши:

```python
@dataclass(frozen=True)
class InputFrame:
    movement: tuple[int, int] = (0, 0)
    pressed: frozenset[str] = frozenset()
    quit_requested: bool = False
```

Например, стрелка вправо и клавиша `D` преобразуются в одинаковое значение `movement=(1, 0)`. В меню те же события преобразуются в действие `"right"` или `"confirm"`.

**Почему здесь уместно:** поддерживаются два набора клавиш, но игровому циклу не нужно знать, каким именно способом игрок подал действие.

**Практический эффект:** при добавлении нового устройства ввода можно создать другой адаптер, который возвращает тот же `InputFrame`, и оставить обработку игры без изменений.

## Мост (Bridge)

**Где находится:** `coin_collector/rendering.py`, абстракция `DrawingAPI` и реализация `PygameDrawingAPI`; сущности используют этот интерфейс в методах `draw()`.

**Задача:** отделить описание внешнего вида игровых объектов от низкоуровневых вызовов конкретной графической библиотеки.

**Как работает:** `DrawingAPI` задаёт набор операций рисования, а `PygameDrawingAPI` выполняет их вызовами `pygame.draw`. Персонаж, монета и опасность описывают изображение через операции этого интерфейса.

```python
class DrawingAPI(ABC):
    @abstractmethod
    def circle(self, color: Color, center: Point, radius: int) -> None:
        raise NotImplementedError

    @abstractmethod
    def rectangle(self, color: Color, rect: pygame.Rect, radius: int = 0) -> None:
        raise NotImplementedError
```

Конкретная реализация соединяет интерфейс с поверхностью Pygame:

```python
class PygameDrawingAPI(DrawingAPI):
    def __init__(self, surface: pygame.Surface) -> None:
        self.surface = surface

    def circle(self, color: Color, center: Point, radius: int) -> None:
        pygame.draw.circle(self.surface, color, center, radius)
```

Сущность рисует себя через абстракцию, не обращаясь напрямую к `pygame.draw`:

```python
def draw(self, drawing: DrawingAPI) -> None:
    r = self.rect
    drawing.rectangle((196, 65, 84), r, 10)
    drawing.circle((255, 255, 255), (r.centerx - 9, r.centery - 2), 5)
    drawing.circle((255, 255, 255), (r.centerx + 9, r.centery - 2), 5)
```

Приложение передаёт сущностям объект-мост, связанный с текущей поверхностью:

```python
self.drawing = PygameDrawingAPI(self.screen)
self.level.player.draw(self.drawing)
```

**Почему здесь уместно:** логика формы и анимации находится у игровых сущностей, а техническая реализация примитивов — в графическом адаптере. Изменить отрисовку или подменить её тестовой реализацией можно без переписывания моделей объектов.

**Ограничение:** другая графическая реализация должна поддерживать все операции, которые вызывает сущность. Этот интерфейс предназначен для простых 2D-примитивов игры, а не для полноценного графического движка.

## Компоновщик (Composite)

**Где находится:** `coin_collector/multiplayer.py`, класс `PlayerComposite`.

**Задача:** одинаково обновлять и отрисовывать всех участников матча, не дублируя циклы для одного и нескольких игроков.

**Как работает:** компоновщик хранит игроков и применяет к каждому соответствующий кадр ввода. Сам `TwoPlayerMatch` обращается к компоновщику так же, как к общей группе игроков.

```python
players = PlayerComposite(level.players)
players.update((player_one_frame, player_two_frame), delta_time, level.bounds)
players.draw(drawing)
```

В режиме на двоих стрелки двигают первого игрока, а WASD — второго. Одиночный режим продолжает принимать оба набора клавиш.

**Почему здесь уместно:** общее движение и отрисовка масштабируются на группу участников, сохраняя индивидуальное управление каждым игроком.

## Декоратор (Decorator)

**Где находится:** `coin_collector/entities.py`, класс `BonusCoin`; бонусные монеты добавляет `GameLevelBuilder.add_bonus_coin()`.

**Задача:** добавить обычной монете дополнительную ценность и заметный внешний вид без изменения её базовой реализации.

**Как работает:** `BonusCoin` оборачивает `Coin`, предоставляет тот же интерфейс `Collectible`, делегирует обновление и отрисовку и удваивает начисляемые очки. При отрисовке он добавляет голубое кольцо.

```python
bonus = BonusCoin(Coin((480, 360)))
assert bonus.value == 20
bonus.update(0.016)  # обновляет обёрнутую монету
```

**Почему здесь уместно:** обычные и бонусные монеты могут находиться в одном списке уровня и обрабатываются одним циклом сбора.

## Фасад (Facade)

**Где находится:** `coin_collector/multiplayer.py`, класс `TwoPlayerMatch`.

**Задача:** предоставить приложению одну точку входа для правил матча: движение игроков, обновление монет, сбор, подсчёт очков и определение победителя.

**Как работает:** приложение передаёт два кадра управления в `update()`, а затем использует итоговые `coin_counts`, `scores`, `finished` и `result_message`. После сбора последней монеты победитель определяется по количеству монет, а бонусная монета при этом остаётся одной монетой, хотя приносит больше очков.

```python
collected = match.update(player_one_frame, player_two_frame, delta_time)
if match.finished:
    print(match.result_message)
```

**Почему здесь уместно:** экран и игровой цикл не содержат подробностей координации двух игроков и правил подсчёта результата.

## Приспособленец (Flyweight)

**Где находится:** `coin_collector/entities.py`, неизменяемый `CoinStyle`; `coin_collector/factory.py`, `CoinStyleFactory`.

**Задача:** не хранить отдельную копию одинаковой палитры в каждой монете.

**Как работает:** фабрика стилей выдаёт общий неизменяемый объект палитры `"gold"`. Прототип монеты и все созданные из него экземпляры используют одну ссылку на этот объект; собственные координаты и анимация у монет остаются независимыми.

```python
factory = ArcadeObjectFactory()
first = factory.create(ObjectKind.COIN, (120, 150))
second = factory.create(ObjectKind.COIN, (840, 150))
assert first.style is second.style
```

**Почему здесь уместно:** уровень содержит много визуально одинаковых монет, поэтому их общие данные стиля можно разделить безопасно благодаря неизменяемости.

## Заместитель (Proxy)

**Где находится:** `coin_collector/audio.py`, класс `SoundEffectsProxy`; приложение передаёт ему текущее состояние настройки звука.

**Задача:** не допускать воспроизведения эффектов и инициализации звукового адаптера, когда звук отключён.

**Как работает:** заместитель предоставляет тот же метод `play()` и проверяет настройку перед передачей вызова реальному `PygameSoundAdapter`. Проверка выполняется для каждого эффекта, поэтому переключение звука в настройках сразу учитывается.

```python
audio = SoundEffectsProxy(sound_adapter, lambda: settings.sound_effects)
audio.play("coin")  # передаётся адаптеру только при включённом звуке
```

**Почему здесь уместно:** игровая логика может запрашивать звук единообразно, а политика доступа к устройству аудио остаётся в прокси.
